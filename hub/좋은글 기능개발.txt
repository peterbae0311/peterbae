확인해보니 "서브도메인"이 아니라 경로 기반(path-based) 단일 도메인 라우팅이고, 이미 이 모노레포 전체가 공유하는 SSO(로그인) 체계가 구축되어 있습니다. 구조는 다음과 같습니다.

1. 도메인/라우팅
- 실제 서브도메인이 아니라 peterbae.duckdns.org 하나의 도메인 아래, nginx가 요청 경로의 첫 path segment로 어느 앱인지 구분합니다 (/shopping-listapp, /lottery, /career 등).
- nginx는 모든 요청 앞단에서 auth_request 서브리퀘스트로 hub의 /api/auth/verify를 호출해 로그인 여부와 앱별 접근 권한을 확인하는 도메인 전체 SSO 게이트를 이미 갖고 있습니다.

2. hub 앱이 이미 하고 있는 일 (Open Question 상당수가 이미 답이 나와 있음)
- 로그인: Supabase Auth 기반 이메일/비밀번호 로그인(hub/src/app/login/page.tsx)이 이미 구현되어 있습니다. → #1(인증 수단) 답변인 "이메일/비밀번호"는 이미 존재하는 체계와 정확히 일치합니다. 좋은글 앱이 새로 auth를 만들 필요 없이 hub의 로그인/세션을 그대로 타면 됩니다.
- 권한 관리: SUPER_ADMIN_EMAIL = 'peter.bae0311@gmail.com'이 hub/src/lib/apps.ts에 이미 하드코딩되어 있고, verify/route.ts에서 이 이메일이면 모든 검사를 통과시킵니다. → #3(삭제 권한: peter.bae0311@gmail.com만)도 이미 있는 SUPER_ADMIN_EMAIL 상수를 그대로 재사용하면 됩니다.
- 일반 사용자별 앱 접근 권한은 Supabase의 app_access 테이블(email + app_key)로 관리됩니다.

3. 배포 방식 (두 트랙)
- Next.js 앱(career, lottery, newsclip, us_stock_market, expo, hub): GitHub Actions에서 빌드(서버가 물리 RAM 500MB라 next build가 OOM 나서 서버에서 직접 빌드 못 함) → SSH로 산출물 전송 → remote-swap.sh가 새 디렉토리 준비 후 원자적 mv 교체 → pm2 reload.
- 정적 사이트(image_slideshow, shopping-listapp 등 9개): 빌드 없이 rsync로 nginx html 루트에 바로 배포.
- 인프라 자체는 Oracle Cloud 컴퓨트 인스턴스(무료 티어, 500MB RAM) + DuckDNS이고, Vercel은 관련 없습니다.

4. Oracle DB 연동 패턴 (좋은글 앱이 참고할 선례)
- image_slideshow는 저장소 루트에는 독립 app.js(구버전/정적 배포용)가 있지만, 실제 최신 Oracle DB 연동 로직은 hub 앱 내부의 API 라우트(hub/src/app/api/image-slideshow/... + hub/src/lib/imageSlideshow/oracleDb.ts)로 옮겨져 있습니다.
- oracledb 드라이버 사용 시 next.config.js에 serverExternalPackages: ['oracledb']를 지정해야 합니다 — 안 하면 라우트별로 별도 인스턴스가 번들링되어 커넥션 풀 캐스팅 오류(NJS-012)가 난다는 것을 실제로 겪고 고친 이력이 있습니다.
